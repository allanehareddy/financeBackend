# Finance Dashboard Backend

A production-quality REST API for finance data processing and role-based access control, built with **Spring Boot 3**, **JWT**, **H2**, and fully documented via **Swagger UI**.

---

## Quick Start

```bash
# Windows
mvnw.cmd spring-boot:run

# Mac / Linux
./mvnw spring-boot:run
```

The app starts at `http://localhost:8080`.  
On first run, it auto-creates the H2 database and seeds 3 demo users + 15 financial records.

---

## Swagger UI (Live API Docs)

**`http://localhost:8080/swagger-ui.html`**

1. Open the URL above
2. Click **POST /api/auth/login** → **Try it out**
3. Paste any demo credential and execute
4. Copy the `token` from the response
5. Click **Authorize** (top-right 🔒) → paste the token → **Authorize**
6. All endpoints are now testable in-browser

## Role-Based Access Control

| Action                  | VIEWER | ANALYST | ADMIN |
|-------------------------|--------|---------|-------|
| View records            | ✅     | ✅      | ✅    |
| View dashboard          | ✅     | ✅      | ✅    |
| Create / update records | ❌     | ✅      | ✅    |
| Delete records          | ❌     | ❌      | ✅    |
| Manage users            | ❌     | ❌      | ✅    |

Enforcement is at two levels:
1. **Spring Security** — route-level via `SecurityConfig`
2. **Method Security** — `@PreAuthorize` annotations on service methods

## Technical Decisions & Trade-offs

### 1. H2 File-Based Database Instead of PostgreSQL
**Decision:** Used H2 in file-persistent mode (`jdbc:h2:file:./financedb`) instead of a full RDBMS.  
**Why:** Zero infrastructure setup — evaluators run one command and the app is live with data. No Docker, no Postgres install, no connection strings to configure.  
**Trade-off:** H2 is not suitable for production (no concurrent write scaling, not cloud-deployable as-is). Migrating to PostgreSQL requires only changing the `pom.xml` dependency and `application.properties` datasource URL — the JPA layer is identical.

### 2. Stateless JWT Over Sessions
**Decision:** JWT tokens stored client-side (Bearer header), no server-side session state.  
**Why:** Naturally scales horizontally — any server instance can validate a token without shared session storage. Also aligns with how SPA frontends (React, Vue) consume APIs.  
**Trade-off:** No built-in token revocation. A logged-out token remains valid until expiry. Mitigated in production via short expiry + a token denylist (Redis). For this assignment, 24h expiry is acceptable.

### 3. Soft Delete for Financial Records
**Decision:** `DELETE /api/records/{id}` sets `deleted = true` rather than removing the row.  
**Why:** Financial data has audit and regulatory implications. Hard-deleting records would break historical summaries (e.g., a past month's totals would silently change). Soft delete preserves history while hiding records from normal queries.  
**Trade-off:** Database grows over time. In production, an archival job would move old soft-deleted rows to a cold storage table.

### 4. In-Memory Token Bucket for Rate Limiting
**Decision:** Implemented a per-IP rate limiter using `ConcurrentHashMap` inside a servlet filter (100 req / 15 min per IP).  
**Why:** No external dependency (no Redis, no API gateway config) while still demonstrating the concept and returning standard `X-RateLimit-*` headers.  
**Trade-off:** State is lost on restart and doesn't work in a multi-instance deployment. A production system would use Redis with sliding window counters or an API gateway.

### 5. Single Service Layer, No CQRS
**Decision:** Business logic lives in `@Service` classes that handle both reads and writes.  
**Why:** CQRS adds indirection that isn't justified for this dataset size. Keeping it simple makes the code easier to follow for an evaluator.  
**Trade-off:** Read-heavy dashboards and write operations share the same transactional path. At scale, separating read models (materialized views or a read replica) would improve dashboard query performance significantly.

### 6. BigDecimal for All Monetary Values
**Decision:** All `amount` fields use `BigDecimal`, not `double` or `float`.  
**Why:** Floating-point types cannot represent decimal fractions exactly (0.1 + 0.2 ≠ 0.3 in IEEE 754). Financial calculations require exact decimal arithmetic. `BigDecimal` with `HALF_UP` rounding is the Java standard for money.  
**Trade-off:** Slightly more verbose code and larger serialized payloads vs primitives.

## Assumptions

1. **Single currency** — All amounts are treated as INR. Currency conversion is out of scope.
2. **Analyst self-service** — Analysts can update any record, not just their own. In a real system this might be scoped per-user.
3. **No email verification** — Users are created active immediately. Production would require email confirmation.
4. **Categories are free-text** — No predefined category enum. This allows flexibility but means "Salary" and "salary" are different categories.
